# 모델·LoRA 최신 확인 절차

사용자는 워크플로를 만들거나 점검할 때 모델과 LoRA가 최신인지 확인하기를 원한다(2026-11-09). 동시에, 잘 나오는 조합을 시험 없이 바꾸는 것은 원하지 않는다(2026-10-14). 그래서 이 절차의 결과물은 교체가 아니라 근거 있는 판정표다. 사용자가 고른 것만 새 파일로 반영한다.

## 1. 원칙

2026-11-09 사용자 지시가 이전 지시보다 우선한다.

- 기능(슬롯)별로 파일 날짜, 좋아요, 다운로드(30일·누적)를 함께 대조한다. Hugging Face와 Civitai를 모두 본다. 날짜와 호환성만 보고 "유지"로 끝내지 않는다.
- 같은 일을 하는 파일 중 더 새롭거나 좋아요·다운로드가 많고 Cloud에서 돌아가면 교체 후보다. 비교 자료가 없다는 이유로 후보에서 빼지 않는다.
- 1순위 후보를 같은 입력과 시드로 기존 파일과 Cloud에서 비교한다. 원본 보존, 색감, 모션, 레퍼런스 반영이 나빠지지 않으면 실제로 교체한다. 떨어진 후보는 파일명과 이유를 표로 남긴다.
- Cloud에 없는 노드 팩이 필요한 후보는 인기와 상관없이 실행 불가로 표시한다.
- 좋아요·다운로드가 저장소 단위 수치이면 그렇게 적는다. 한 저장소에 파일이 여러 개면 파일별 인기를 알 수 없다.
- 같은 점검에서 겹치는 워크플로, 무거운 원인, 파일별 터보 적용 가능 여부도 본다. 개선하면서 그래프가 무거워지면 안 된다.
- WAN은 우선순위가 가장 낮다. H3와 LTX를 끝내고 시간이 남으면 마지막에 한다.
- 시험은 기존 파일이 아니라 새 복사본에서 한다.
- 측정이 없으면 품질이 좋다고 쓰지 않는다.
- 제작자가 스스로 밝힌 성능은 "제작자 수치"로 표시하고 우리 측정과 섞지 않는다.

## 2. 확인 순서

### 2-1. 사용 중인 파일 목록을 뽑는다

`python3 -I tools/audit_models.py <파일이나 폴더> [--since YYYY-MM-DD] [--list-only]`를 쓴다. 공개 HF API만 익명으로 조회하고, 확인하지 못한 저장소가 있으면 종료 코드 1을 돌려준다. 이 도구는 변경 후보를 찾아 줄 뿐 판정은 하지 않는다. 안쪽 노드까지 `widgets_values`와 `properties.models`를 모두 본다. `Owner__Repo__file` 이름은 저장소로 되돌려야 하는데, Cloud 이름에서 저장소의 점이 빠져 있으므로 작성자의 저장소 목록과 점을 뺀 이름으로 맞춰 찾는다.

### 2-2. 저장소가 아니라 파일 단위 날짜를 본다

저장소의 `lastModified`는 README나 라이선스만 고쳐도 바뀐다. 2026-10-22의 Lightricks 저장소 갱신은 README 라이선스 수정이었고 가중치는 그대로였다. 파일 날짜는 tree API로 본다.

```
# 저장소 정보: lastModified, downloads, likes, gated
https://huggingface.co/api/models/<owner>/<repo>

# 파일별 날짜, 크기, LFS sha256 (expand=true가 있어야 lastCommit이 나온다)
https://huggingface.co/api/models/<owner>/<repo>/tree/main?recursive=true&expand=true&limit=1000

# 같은 작성자의 다른 저장소, 최근순
https://huggingface.co/api/models?author=<owner>&limit=200&sort=lastModified&direction=-1
```

파일이 많으면 응답의 `Link` 헤더로 다음 페이지를 받는다. `lastCommit.date`가 파일 날짜다. 작성자의 형제 저장소까지 봐야 새 줄기를 놓치지 않는다.

### 2-3. 고정된 커밋에서 sha를 비교한다

워크플로가 `resolve/<commit>/` URL을 쓰면 `tree/<commit>`과 `tree/main`의 `lfs.oid`를 비교한다. 같으면 그 파일은 바뀌지 않았다. 파일명이 달라도 같은 oid면 미러다. 2026-11-09 예: Comfy-Org의 fl2v Turbo 8스텝 v1.0은 lightx2v 파일과 LFS 해시가 같았다.

링크는 `HEAD`로 302 뒤 200이 나오는지 확인한다.

### 2-4. 같은 줄기의 후속인지 확인한다

이름이 비슷해도 다른 계열일 수 있다. 2026-11-09 예: CausVid v2(624키, rank 32, 어텐션 레이어만)와 lightx2v T2V rank64(1459키, 전체 블록, diff 패치 포함)는 후속 관계가 아니라 다른 LoRA다. 모델 카드의 base model, 제작자 설명, 키 구조로 판단한다. 파일 메타데이터의 베이스 표기는 믿지 않는다. lightx2v 파일은 REF2V도 메타데이터에 fl2va로 적혀 있었다.

### 2-5. 변경 내용을 찾는다

모델 카드, 커밋 메시지, 토론 글, 제작자 깃허브 표를 본다. 커밋 제목만 있고 설명이 없으면 "변경 내용 미공개"로 적는다. 2차 사이트와 제작자 설명이 다르면 제작자를 따른다. 2026-11-09에 comfyui-wiki의 6/3 표기가 제작자의 12/3 설명과 달랐다.

### 2-6. 파일 헤더를 읽는다

safetensors는 앞 8바이트가 헤더 길이다. HTTP Range로 헤더만 받아 키, shape, dtype, 메타데이터를 비교한다. 전체를 받을 필요 없다. 키가 같으면 같은 로더로 불러올 가능성이 높다는 뜻이고, 품질이 같다는 뜻은 아니다. rank와 alpha도 비교한다. ComfyUI는 alpha/rank로 스케일하므로 같은 강도 1.0이라도 실제 세기가 다르다.

### 2-7. 레시피와 실제 실행 경로를 비교한다

- 스텝, 샘플러, 스케줄러, shift, 강도가 제작자 권장과 현재 그래프에서 같은지 본다. 하나라도 달라지면 파일 교체가 아니라 그래프 변경이다.
- 그 모델이 기본 설정에서 실제로 실행되는지 추적한다. 2026-11-09 예: Gemma e2b 프롬프트 인핸서는 스위치가 꺼져 있어 파일을 바꿔도 결과가 바뀌지 않았다.
- 제작자 워크플로가 Cloud에 없는 노드를 요구하면 그대로는 못 쓴다. "native nodes"라고 적혀 있어도 JSON의 노드 목록을 직접 본다.

### 2-8. Cloud에서 쓸 수 있는지 본다

`object_info`로 노드를, `/experiment/models`와 `/assets`로 모델을 확인한다. 내장 파일이면 원래 이름, 가져와야 하면 `Owner__Repo__file` 이름이다. 자세한 내용은 `references/클라우드_사실.md`에 있다.

### 2-9. 판정하고 반박 검증을 거친다

아래 3절과 4절을 따른다.

## 3. 판정 어휘

파일 조사 단계의 상태는 `latest`, `newer_available`, `unknown`으로 적는다. 후보별 최종 판정은 아래 네 가지만 쓴다.

| 판정 | 뜻 | 조건 | 다음 행동 |
|---|---|---|---|
| `keep` | 유지 | 후속이 없거나, 후속이 아니거나, 측정상 현재가 낫거나, 교체가 의미 없다 | 그대로 둔다 |
| `swap_in_place` | 파일만 교체 가능 | 같은 줄기, 같은 베이스, 같은 로더, 같은 키, 같은 권장 레시피, 공개된 변경 내용이 모두 충족되고 Cloud에서 로드 확인 | 사용자 승인 후 새 파일로 반영하고 다시 실행 |
| `add_as_option` | 선택 옵션으로 추가 | 다른 용도이거나 기본을 바꿀 근거는 없지만 쓸모가 있다 | 시험 후 끄고 켜는 옵션 또는 새 파일 |
| `needs_ab_test` | 비교 전에는 알 수 없음 | 교체 후보이나 레시피가 다르거나 변경 내용이 미공개이거나 측정이 없다 | 새 복사본에서 A/B. 끝날 때까지 현재 유지 |

2026-11-09 조사에서 `swap_in_place`로 살아남은 항목은 0건이었다. 드문 판정이다.

## 4. 반박 검증

처음 판정을 낸 쪽과 다른 관점에서 "이 판정이 틀렸다"를 증명하려고 시도한다. 가능하면 별도 에이전트에게 맡긴다. 2026-11-09 조사에서 이 단계가 잡아낸 오류는 다음과 같다.

- 현재 파일의 날짜를 후보 파일 날짜로 적은 경우.
- 예전 A/B가 그 파일 쌍을 비교한 것처럼 인용한 경우. 2026-11-07 A/B는 v0.1과 28스텝을 비교했고 v1.0과는 비교하지 않았다.
- 예전 A/B의 범위를 넘겨 해석한 경우. 그 LoRA를 쓰는 파일 4개 중 스텝 비교를 직접 한 것은 아웃페인팅뿐이었고, HeadSwap, CharacterSwap, 프리비즈는 단일 GPU 성공만 있었다.
- 스텝 수가 이상하다고 지적했는데 실제로는 노드 제목에 제작자 기본값으로 적혀 있었던 경우.
- 인핸서 경로가 꺼져 있어 교체 효과가 없는 경우.
- 다른 계열 LoRA를 후속으로 부른 경우.
- 근거를 확인하지 않은 평가 문구를 그대로 믿은 경우. 파일명의 평가 문구가 다른 파일의 것이었다.

확인할 것은 다음과 같다.

- URL이 200을 돌려주는가, 파일 크기가 맞는가.
- 파일 날짜가 정말 그 파일의 날짜인가.
- 인용한 문장이 정말 그 문서에 있는가.
- 기존 측정이 정말 이 쌍을 비교했는가.
- 현재 그래프의 실제 설정이 권장 레시피와 무엇이 다른가.
- 그 경로가 기본값에서 실행되는가.
- Cloud에서 쓸 이름이 정해졌는가.

## 7. 라이선스

MiniMax H3 Community License 원문은 적용 제외 지역에 EU, 영국, 대한민국, 미국을 올리고 있고, 제한이 Output과 파생 모델에도 미친다(2026-11-09 원문 확인, 법률 자문 아님). H3 계열 파일을 상업 납품에 쓰기 전에 사용자가 검토하도록 보고에 한 줄 적는다. 별도 라이선스 경로는 MiniMax에 문의하는 것이다. 모델 확인 보고에서는 게이트 여부와 함께 라이선스 변경도 본다. Lightricks 저장소도 2026-10-22에 라이선스 문구가 바뀌었다.

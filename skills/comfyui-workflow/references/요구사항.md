# 사용자 요구사항

2026-09-24부터 2026-11-09까지 사용자가 낸 지시와 작업 중 확정된 관례를 주제별로 정리했다. 괄호의 날짜는 지시가 나온 날이다. 충돌하는 지시는 가장 늦은 것을 남겼다. "관례"는 사용자가 직접 말하지 않았지만 납품본에서 굳어졌고 이의가 없었던 항목이다.

## 1. 그래프 구조

- 모든 워크플로는 `입력 노드 → 메인 서브그래프 노드 1개 → 저장 노드`로 만든다(2026-09-24, 2026-10-23, 2026-11-08). 2026-11 스냅샷 50개 중 37개가 최상위 서브그래프 1개 구조다. 나머지 13개는 `90_` 폴더 4개, 최상위 서브그래프가 없는 `log변환기` 1개, 최상위 서브그래프가 2~4개인 파일 8개다. 이 구조만으로 결함으로 보지 않고, 누락되었거나 쓰기 불편한 파일만 고친다.
- 사람이 바꾸는 값은 메인 노드에 노출한다. 프롬프트, 길이, 해상도, 시드, 모드, 품질/속도, 스위치, 모델·LoRA·VAE 선택이 해당한다. 공식 Wan2.2 이미지→영상 템플릿의 메인 노드가 목표 형태다(2026-10-04, 2026-11-08).
- 시각적 그룹만 만들거나 모든 조작을 안에 숨긴 파일은 미완료다(2026-11-08). 최상위에 노드를 풀어 놓고 그룹으로만 나눈 구성은 원하지 않는다(2026-10-04).
- 영상·이미지 로드 노드, 저장 노드, 트랙·박스·페인터 같은 대화형 에디터는 서브그래프 밖에 둔다. 모델 로더, 전처리, 샘플링, 후처리는 안에 넣는다(2026-10-14 관례, 2026-11-08).
- 서브그래프 안은 제목 있는 번호 그룹으로 나눈다. 모델 로드, LoRA·모델 패치, 설정값, 프롬프트, 입력·크기·길이, 단계별 샘플링, 디코드·출력 순이다(2026-10-04). 2026-11 스냅샷에서 많이 쓰는 제목은 `01  모델 · 로딩 / LoRA`, `02  설정 · 프롬프트 / 시드`, `03  입력 정리 · 크기 / 길이`, `04  조건 · 프롬프트 / 가이드`, `05  생성 · 샘플링 / 처리`, `06  복원 · 디코드 / 합성`, `07  출력 · 확인 / 저장`이다.
- 이미 서브그래프가 있는 파일은 재사용한다. 누락되었거나 쓰기 불편한 파일만 고친다(2026-11-08).
- 새 워크플로는 같은 폴더의 기존 파일에서 노드 형태를 복제해서 만든다(2026-11-08 관례).
- 공식 템플릿이나 외부 워크플로를 그대로 붙여 넣어 납품하지 않는다. 메인 컨트롤러, 한국어 위젯, 입력·편집·결과 그룹, 자동 처리를 넣는다. 템플릿의 예제 이미지, 예제 프롬프트, 랜덤 시드는 기본값으로 남기지 않는다(2026-11-06).
- 노드는 최소로 쓴다. 문어발처럼 늘어놓지 않고, 무겁지 않게, 작업자가 나중에 고치기 편하게 만든다(2026-09-24, 2026-10-04, 2026-10-13).
- 사용자가 직접 마스크를 넣는 작업에 자동 마스크나 리라이트 같은 부가 단계를 끼우지 않는다(2026-10-23).
- 수정을 덧붙이며 늘어난 노드는 필수·선택·중복으로 분류하고 확정된 최종 로직만 남긴다(2026-09-26).
- 긴 파이프라인은 단계별 덩어리로 나눠, 생성 모델 교체나 다른 그래프로의 이동을 통째로 할 수 있게 만든다(2026-10-23).
- 효과 추가 단계는 선택 사항이므로 빈 자리나 바이패스로 둔다. 전경·매트·배경의 최종 합성은 맨 마지막에 한다. 효과 노드는 배경 플레이트에만 끼워 피사체 원본을 건드리지 않게 하고, 합성의 세 입력은 같은 규격 맞춤 단계를 거친 것만 쓴다(2026-10-23).
- 위젯 라벨, 그룹명, 안내문은 한국어로 쓴다. 영어 원본 이름이나 중복 번호를 남기지 않는다(2026-10-04 관례).
- 안내는 짧은 사용법 노트와 모델·설정·한계 상세 노트로 나눈다. 모델 다운로드 주소는 모델을 불러오는 안쪽 노드의 `properties.models`에 `{name, url, directory}`로 넣는다(2026-11-07 관례). `directory`는 그 로더가 읽는 폴더다(`ModelPatchLoader`는 `model_patches`). `name`은 Cloud에서 쓰는 이름과 같아야 한다.
- 한 번 실행의 최종 저장은 1개다. 비교, 미리보기, 1차 결과는 저장하지 않는다. 예외는 패스 추출처럼 결과가 원래 여럿인 파일과 사용자가 고른 멀티모델 비교 원본이다(2026-10-13, 2026-10-23).
- Cloud에서 추가 설치 없이 돌아가야 한다. 코어 노드와 Cloud 사전 설치 팩(KJNodes, WAS, layerstyle, Image-Filters 등)만 쓴다(2026-11-08).
- 각 모델에 생성 워크플로를 만들 때는 T2V, I2V(첫 프레임 + 선택 끝 프레임, 이미지 한 장만으로도 실행), V2V를 갖춘다(2026-10-14). 2026-11 스냅샷에는 일반 영상 생성 폴더가 없고, 그 경위는 확인되지 않았다. 사용자가 생성 폴더를 요청할 때 적용한다.

## 2. 배치와 색

- 메인 화면은 입력 왼쪽, 프롬프트·핵심 설정 가운데, 결과와 선택 추출 오른쪽, 안내문 아래의 흐름이다. 파일마다 배치가 달라지면 안 된다(2026-11-08).
- 최상위 캔버스는 번호 붙은 한글 그룹과 안내로 구성한다(2026-10-14~2026-11-08). 새 파일의 기본 제목은 `01 입력 · 이 칸부터`, `02 편집`, `03 결과`, `안내 · 입력 조건 / 보존 범위`이다(2026-11 스냅샷 최빈값 23, 22, 22, 10개).
- 노드 색은 역할별로 진하게 구분한다(2026-09-30, 2026-10-14). 2026-11 스냅샷의 최빈값은 아래와 같다. 새 파일이나 가져온 파일도 납품 전에 맞춘다.

| 역할 | 계열 | color | bgcolor |
|---|---|---|---|
| 입력 | 파랑 | `#477eac` | `#252d38` |
| 메인 컨트롤 | 보라 | `#8870ae` | `#252d38` |
| 저장 | 초록 | `#5b946f` | `#252d38` |
| 안내 | 갈색 | `#897343` | `#252d38` |

- 노드 겹침 0, 그룹 밖 노드 0, 제목 잘림 없음, 수천 픽셀짜리 빈 공간 없음. 처음 불러온 화면이 바로 쓸모 있어야 한다. 겹침은 제목 30px까지 포함한 사각형으로 전 파일을 검사한다(2026-10-14, 2026-11-08).
- 좌표와 크기는 15의 배수로 준다. Cloud가 불러올 때 15px 격자에 맞추기 때문이다(2026-11-08 측정).
- 물려받은 배치 위에 노드만 더하거나 빼서 넘기지 않는다. 파일마다 라이브러리 배치를 새로 적용한다(2026-10-14).
- 배치 수정은 위치, 크기, 그룹만 바꾼다. 모델, LoRA, 프롬프트, 시드, 스텝, 링크, 모드를 건드리지 않았음을 전후 실행 API 동일성으로 증명한다. GPU 재생성은 필요 없다(2026-11-08).
- 지목된 파일과 같은 결함이 있는 다른 파일도 실제 화면을 확인한 뒤 같이 고친다. 실행 의미는 보존한다(2026-11-08).
- 배치 확인은 Cloud 프런트엔드의 실제 화면과 렌더링 좌표로 한다. JSON 좌표나 캔버스 내보내기로 판단하지 않는다(2026-11-08).

## 3. 크기·길이·FPS 자동화

- 입력에서 가로, 세로, 프레임 수, FPS를 읽어 모델 규격(배수, 프레임 공식)에 자동으로 맞추고, 생성 후 원본 크기·길이·FPS로 되돌린다. 작업자가 직접 계산해 넣게 하지 않는다(2026-09-26, 2026-10-22, 2026-11-06).
- 자동 처리 필수 항목은 입력 크기·길이 검사, 모델 규격 맞춤, 원래 길이로 자르기, 추론 크기 맞춤, 원본 크기·FPS 복원이다(2026-11-06).
- 출력은 원본의 W, H, 프레임 수, FPS와 정확히 같아야 한다. 프레임 드랍과 임의 크롭은 허용하지 않는다(2026-09-26, 2026-11-08).
- 이 일치 규칙은 원본 영상을 편집하는 파일에 적용한다. 기능 자체가 규격을 바꾸는 파일은 그 항목만 예외다. 아웃페인팅은 W×H, 영상 연장은 프레임 수, 프레임보간·슬로모션은 프레임 수와 FPS, 업스케일은 W×H가 달라진다.
- 모델 프레임 규칙 때문에 원본 끝을 잘라내지 않는다. 패딩해서 생성하고 원래 길이로 되돌린다(2026-10-04, 2026-11-08).
- 생성 해상도는 메가픽셀 값 하나로 정하고 가로세로는 원본 종횡비와 모델 배수에 맞춰 계산한다. 고정값으로 두지 않는다(2026-09-30).
- 길이 제한 위젯의 기본은 0(원본 전체)으로 둔다. 기본값이 숫자로 남아 있으면 그보다 긴 영상이 조용히 잘린다(2026-11-09 점검에서 파일 2개 발견).
- 규격이 어긋나면 잘못된 결과를 저장하지 말고 멈춘다. 단 29.97처럼 표기만 다른 FPS에서 멈추면 안 된다(2026-10-22~2026-11-01). 허용 오차는 `references/노드_함정.md`에 있다.
- VFX 결과는 시간축이 원본과 일치해야 한다. 결과 k번 프레임이 원본 k번 프레임과 대응하고 마스크도 밀리면 안 된다(2026-09-26, 2026-10-14).
- 하드컷이 있는 영상은 컷별 생성을 시험한다. 컷마다 최소 길이까지 패딩하고 생성 후 원래 길이로 잘라 원래 순서로 이어 붙인 뒤 원본 FPS와 프레임 수를 복원한다(2026-11-08).
- 시드는 스테이지별로 두지 않고 바깥 시드 하나로 묶는다(2026-10-23, 2026-11-01). 2단계 시드가 따로 놀아 재현이 안 되던 것이 결함으로 지적됐다.
- 납품 파일의 시드 컨트롤 기본값은 `fixed`다(2026-11 스냅샷 위젯 fixed 204, randomize 12). randomize 12개는 모두 `90_` 폴더의 유료 API 노드다. 2026-10-23의 '효과 노드 시드 랜덤' 지시는 파일 1개에 대한 것이다.
- 소리는 이렇게 처리한다. 납품용 영상의 기본 출력은 무음이다(2026-10-14, 2026-11 납품본에서 50개 중 46개가 유지). 소리를 쓰는 파일은 모델 생성 효과음을 기본으로 끄고 원본 소리만 쓴다(2026-11-01, 24fps가 아닌 영상에서 생성 오디오가 어긋난 것이 근거). 어느 쪽이든 오디오 트랙이 없는 소스에서 멈추면 안 된다(2026-09-26).
- 규격 일치가 원본 해상도의 디테일을 뜻하지는 않는다. 약 1MP로 생성해 키운 결과는 크기만 원본이고 디테일은 1MP급이라고 노트에 적는다(2026-10-23).

## 4. 색과 프레임 보존

- VFX 편집은 원본을 유지하고 제어하려는 부분만 바꾼다. 인물의 모션과 외형은 그대로 두고 교체 대상만 바뀌어야 한다(2026-09-24).
- 수정 대상 밖의 색감, 명암, 움직임, 프레임은 원본과 같아야 한다. 합격 기준은 '바꾼 곳만 바뀌었는가'다(2026-10-13, 2026-10-23, 2026-11-07). 보호 구역은 색까지 원본과 같아야 하며, 최종 단계에서 실제로 원본 픽셀로 덮이는지 확인한다(2026-10-23).
- 이미지 레퍼런스의 색도 그대로 반영되어야 한다. 레퍼런스대로 바뀌지 않거나 조명·시간대가 임의로 바뀌는 모델 조합은 기본값으로 두지 않는다(2026-09-26, 2026-10-14).
- 색이 틀어지면 보정 노드를 덧대기 전에 모델 제작자의 프롬프트 가이드에 맞춰 원인부터 제어한다(2026-10-14).
- 첫 프레임 편집 전파에는 결과 0번 프레임을 참고 이미지 색에 맞추는 보정을 넣을 수 있다(2026-10-15). 컷 1개, 참고 이미지 1장으로만 측정됐으니 다른 조건은 미검증이라고 적는다.
- 원본 합성은 AI 영상과 이질감이 없어야 한다. 경계가 티 나거나 마스크 색이 테두리에 번지면 안 된다. 목표는 WAN VACE급이다(2026-09-24, 2026-09-26).
- 뭉개짐과 화질 저하가 없어야 한다. 2단계 생성에서 디테일이 무너지면 안 되고 첫 프레임부터 좋아야 한다(2026-09-26, 2026-10-04, 2026-10-23).
- VFX 기본 경로는 latent 파일을 주고받지 않는 방식으로 하고, 색 틀어짐 위험이 있는 2패스 정제는 기본으로 두지 않는다(2026-10-14).
- 마스크가 없는 경로를 '픽셀 보존'이라고 부르지 않는다. 모든 경계 픽셀이 원본과 같다고 주장하지 않는다. 모델 자체 보존과 마스크 합성 보존은 구분해서 적는다(2026-11-07).
- 입력이 달라져도 잘 나오는 범용 기본값을 먼저 챙긴다. 다만 설정만으로 성공률을 보장할 수 있다고 말하지 않는다. 마스크 방향과 품질, 프롬프트는 사람이 맞춰야 할 몫으로 안내한다(2026-11-01).
- 아웃페인팅 이음새를 숨긴다. 페더는 고정 16px 대신 원본 세로의 약 4%로 하고, 경계 색을 맞추며, 저장 전 얇은 복원 패스로 질감을 맞춘다(2026-11-01). 2026-11-09 작업본의 LTX 아웃페인팅 `원본 경계 페더 폭 (px)` 값은 16이다. 시험 없이 기본값을 바꾸지 않는다.
- 업스케일은 샤프닝이 아니라 원본을 살리고 디테일만 더하는 방식이다. 저주파 차이 같은 수치로 많이 바뀌지 않았음을 확인한다(2026-11-06).
- 가는 오브젝트 클린 작업은 선 단위로 하지 않는다. 대체 소스를 정확히 정합한 뒤 넓은 덩어리로 페더를 줘 얹는다. 시간축에서 나타났다 사라지는 현상, 인물·손의 일그러짐, 구멍을 원본과 대조한다(2026-10-24).
- LOG 납품은 카메라를 고르게 하지 않는다. AI 결과와 원본 LOG 영상 두 개를 넣으면 원본 LOG와 같은 색감으로 나오게 하고, 바꾸지 않은 영역은 선택 마스크로 원본에 붙일 수 있게 한다(2026-11-08). 화질 저하가 없는지 수치로 확인한다(2026-11-06). Cloud에서 완전 비압축 파일을 받을 수 없으니 ProRes 4444 10bit, 16bit PNG 시퀀스, EXR 시퀀스로 내고 이 차이를 안내문에 적는다. 실제 카메라 LOG로 시험했는지도 밝힌다.

## 5. 입력, 마스크, 참조 이미지

- 라이브러리는 클린플레이트, 인페인팅, 아웃페인팅, 길이연장(인물 연결성 유지), 뎁스맵·프리비즈→이미지 레퍼런스 교체를 핵심 VFX로 보장한다(2026-10-13).
- VFX용 워크플로는 원본 영상을 넣어 편집하는 V2V이고 참고 이미지 입력도 받을 수 있어야 한다(2026-10-21).
- 인페인팅 계열은 사용자가 만든 마스크 영상을 직접 넣을 수 있어야 한다. 마스크 기반 워크플로에는 가능하면 자동 추적을 끼우지 않는다(2026-09-24, 2026-09-26). 마스크 기반 교체의 입력은 원본 영상, 이미지 레퍼런스, 흑백 마스크 영상 세 칸이다.
- 마스크는 흰색이 바꿀 곳, 검정이 보호 영역이다. 마스크를 받는 파일에는 기본 꺼짐의 '마스크 반전' 스위치를 둔다(2026-10-14, 2026-10-21, 2026-10-22).
- 넣은 마스크는 수치를 건드리지 않아도 그대로 잘 반영돼야 한다(2026-10-23). 마스크를 입력으로 받는 편집 파일은 '마스크 반전'을 메인 노드 위젯으로 둔다(2026-10-14). 확대, 축소, 페더는 조절이 필요할 때만 쓰도록 메인 서브그래프 밖 `마스크 · 확대 / 페더 / 인버트` 그룹으로 뺀다. 마스크를 만들어 내보내는 08 폴더 파일은 인버트도 메인 밖에 둔다.
- 마스크를 대충 따도 잘 작동해야 한다. 경계에 여유를 줄 수 있게 한다(2026-09-24).
- 생성과 합성은 같은 확장 마스크를 쓴다. WAN VACE 범용 기본값은 확장 2px, 페더 2px이다. 배경 교체는 0~2, 인물·물체 교체는 8~16으로 올린다. 페더 0은 경계가 계단 지므로 피한다(2026-11-01). 이 값의 근거는 결과 영상 1쌍과 구조 확인이고 렌더 재측정은 없었다.
- '제거' 워크플로가 마스크를 요구하면 이름과 안내에 밝힌다. 사람·물체 제거의 기본 기대는 마스크 없이 되는 것이고, 마스크 없는 제거와 마스크 인페인팅은 다른 파일로 나눈다(2026-10-13, 2026-10-14, 2026-10-22).
- 로토·추적은 SAM 3.1을 쓴다(2026-09-24). 알파 영역은 별도 영상으로 뽑아 후반 합성에서 트랙매트로 쓸 수 있게 하되, 매트 출력은 로토·마스크 전용 파일에서 제공한다(2026-09-24, 2026-10-13 이후).
- 이미지 편집 워크플로는 이미지1=원본, 이미지2=레퍼런스로 고정한다. 결과 구도와 크기는 이미지1을 따르고, 이미지2 슬롯은 연결하거나 지우거나 뮤트해도 실행돼야 한다(2026-10-23).
- 참고 이미지 하나를 쓰려고 이미지 노드와 스위치를 따로 켜게 하는 구조를 피한다. 불가피하면 왜 둘 다 필요한지 노드 제목과 노트에 쓴다(2026-10-22).
- WAN VACE 참고 이미지는 잘라내지 않는다. 비율을 유지해 흰 여백으로 맞추고, 투명 PNG는 흰 배경에 합성해서 넣는다(2026-11-01, 정적 확인까지).
- 아웃페인팅은 별도 참고 이미지 없이 원본 영상만으로 돌아가야 한다. 종횡비는 ◀▶로 넘겨 고르면 자동 확장되고, 목록에 없는 비율도 W:H로 입력할 수 있어야 한다(2026-10-21). 2026-09-27에 이미지 레퍼런스 입력도 요청됐으므로 선택 입력으로는 둘 수 있다.
- 참조 이미지는 이미지 생성으로 후보를 뽑되 그대로 넣지 않는다. 바꾼 부분만 원본 프레임에 합성해서 쓴다. 생성 이미지를 그대로 넣으면 영상과 색감이 달라진다(2026-11-08).
- 참조 이미지를 전체 프레임 재생성으로 만들지 않는다(2026-11-07). 후보 이미지는 Cloud의 GPT 이미지 노드로 뽑을 수 있다. 파트너 노드이므로 사용자 승인 범위 안에서 돌린다(2026-11-08).
- 교체용 참조는 교체 대상만 다르고 나머지는 원본과 같아야 한다. 합성은 원본 크기에 맞춰 무손실 PNG로 저장하고, 경계 블렌딩 영역은 마스크에 포함하며, 마스크 밖 차이를 검사한다(2026-11-07).
- 손이나 든 물건처럼 앞을 가리는 전경은 원본을 유지한다. 보호 영역은 실제 전경 위치의 좁은 범위로 한정해서, 새 옷이 덮어야 할 곳까지 보호하지 않는다(2026-11-07).
- 참조 합성은 마스크 밖 차이 0만으로 합격시키지 않는다. 전체 프레임과 경계 확대를 직접 보고 잔여물과 외곽 훼손을 확인한다(2026-11-07).
- 제품 사진만 받는 경로인지 편집된 키프레임이 필요한 경로인지 구분해 안내문에 적는다. 교체 성공이 리무브 성공을 뜻하지 않으므로 기능별로 따로 판정한다(2026-11-08).
- 구도가 다른 컷의 참조를 다음 컷의 첫 프레임으로 쓰지 않는다. 참조는 컷별로 맞춘다(2026-11-08).
- 일반 VFX 파일과 FFP 파일은 별도로 제공한다. FFP 파일은 사용자가 모델을 바꾸지 않아도 `_ffp` LoRA, 수정 첫 프레임 입력, `vfx_edit:` 시작과 `<Picture 1>` 역할 명시까지 된 상태여야 한다(2026-11-08).

## 6. 프롬프트

- 프롬프트는 모델별 공식 트리거, 이미지·비디오 토큰, 참조 역할을 따른다. 바꿀 대상, 원하는 결과, 보존 요소를 구체적으로 쓰고, 실제 인코더에 들어간 문장까지 확인한다. 모든 모델에 같은 문장을 쓰지 않는다(2026-11-07).
- 접두사는 H3 VFX·FFP는 `vfx_edit:`, H3 HeadSwap은 `head_swap:`, H3 style transfer는 `style_transfer:`, Alissonerdx character swap은 `body_swap:`, LTX EditAnything은 `edit_anything:`이다(2026-10-14, 2026-11-08, 제작자 문서 기준).
- FFP에는 `<Picture 1>`이 이 클립의 수정 첫 프레임이라고 쓴다. 그 프레임의 색과 내용을 글로 묘사하지 않는다. 묘사하면 모델이 이미지보다 글을 따른다(2026-10-14, 제작자 프롬프터 규칙). 국소 편집에는 자세, 움직임, 구도, 조명, 색을 지키라는 문장을 넣는다.
- H3 V2V 편집 프롬프트에는 재생 속도와 프레임 대응을 명시하는 문장을 넣는다. "its motion timing and playback speed define every frame", "each frame shows the same moment as the same frame of <Video 1>", "at the original playback speed"를 넣어 짧은 클립 1건에서 모션 상관이 0.06에서 0.94로 올랐다(2026-10-22). 2~15초 범위는 참조 영상(`ref_videos`)에 대한 것이다(라이브러리 노트 기록, 공식 문서로 재확인하지 않음).
- 리무브 프롬프트는 삭제 지시, 빈 배경 복원, 카메라·조명·무관한 배경 보존을 쓴다. 인물을 보존하라는 기존 문장은 뺀다. 인페인팅 경로에서는 남은 빈 장면만 묘사한다(2026-11-08). "Remove the ..." 문구가 새 인물을 만든 시험이 있었다.
- 납품 파일의 기본 프롬프트는 완성된 문장이어야 한다. 끊긴 문장이나 내용 없는 지시를 남기지 않는다(2026-11-01).
- 테스트는 워크플로 용도에 맞는 프롬프트를 직접 써서 돌린다. 기본값이나 자리표시 프롬프트로 판정하지 않는다(2026-10-21~2026-11-01).
- 성공한 설정, 입력, 프롬프트는 기본값이나 재현 프리셋, 안내문에 반영해서 사용자가 그대로 재현할 수 있게 한다(2026-11-08).

## 7. 이름과 폴더

### 파일 이름

형식은 `폴더내순서_모델+버전_기능_입력조건_실측초[_모델별순위].json`이다(2026-11-08). 예: `02_Pika_Ref2VA_사물교체_제품사진1장_50초_H3-02.json`.

- 맨 앞 `01`, `02`는 같은 폴더 안 순서다. 끝의 `H3-01`, `LTX-01`은 폴더를 넘어선 모델별 순서다. '1등', '1위'로 쓰지 않는다(2026-11-08).
- 끝의 초는 Cloud 실측 시간이다. 측정 조건은 루트 `00_어떤걸쓸까.md`에 적는다. 실측이 없으면 초를 넣지 않는다(2026-11-08). 2026-11 스냅샷의 기준은 576×1024, 73프레임이다.
- 기존 번호를 밀지 않고 새 파일을 맨 앞에 넣어야 하면 `00_`을 붙인다(2026-11-08).
- 이름만 봐도 무엇을 하고 무엇이 필요한지 알 수 있어야 한다. `3-2` 같은 뜻 없는 코드는 쓰지 않는다. 모델 버전은 항상 넣는다(2026-10-13, 2026-10-14).
- 마스크 필요 여부를 이름에 쓴다. 마스크필요, 마스크없음, 마스크+첫프레임 등이다(2026-10-14).
- 한계가 있는 파일은 이름에 그 한계를 쓴다. 예: `원경1명만_근접실패`(2026-11-08).
- 메인 노드 제목은 파일의 모델과 기능을 ` · `로 이어 쓴다. 저장 접두어는 모델이나 기능 이름으로 시작한다(예: `H3_FFP/result`). 2026-10-14에는 파일명과 같게 맞췄지만 2026-11-08에 앞 번호와 실측초가 붙으면서 달라졌다. 2026-11 스냅샷 50개 중 제목이 파일명과 글자까지 같은 파일은 0개, 접두어 끝이 앞 번호와 실측초를 뺀 파일명과 같은 파일은 1개다. 이 차이만으로 기존 파일을 고치지 않는다.
- 사용자가 파일명에 붙인 `ok_` 같은 상태 표시는 재빌드와 이름 변경 때 유지한다. 표시 없는 중복본을 만들지 않는다(2026-10-21~2026-10-23).

- 루트에 상황별 선택 안내 `00_어떤걸쓸까.md`와 옛 경로·새 경로 대응표를 둔다(2026-11-08). 겉보기에 똑같아 고르기 어려운 파일은 합치거나 어떤 경우에 무엇을 쓸지 분명히 안내한다(2026-10-14). 대응표를 ZIP이나 저장소에 실제로 넣었는지 확인한다. 2026-11-09 받은 묶음에는 안내문이 가리키는 `검증결과/워크플로_경로변경표.csv`가 없었다.
- 폴더링 요청은 문서 작성이 아니라 실제 폴더를 만들어 옮기라는 뜻이다. 끝나면 위치를 정확히 알린다(2026-10-23).
- 성인용처럼 따로 취급할 워크플로는 최상위 별도 폴더로 분리한다(2026-10-23).

## 8. 중복 제거

- 복사·붙여넣기로 비슷해진 파일은 비교해서 대표 하나만 개발하고 제외 사유를 적는다(2026-10-13). 기능별로 어떤 영상에나 쓸 수 있는 마스터본을 지향한다(2026-10-04).
- 그래프가 같고 LoRA, 샘플러, 스텝만 다른 변형은 토글이 있는 파일 하나로 합친다. 같은 작업에 파일을 여러 개 두지 않는다(2026-11-06).
- 스텝 수 등 값만 다른 변형은 한 번에 돌아가면서 품질이 좋은 쪽을 남긴다(2026-10-23). 측정상 같으면 가벼운 쪽을 남긴다(2026-11-07).
- 본체 모델이 다르면 중복이 아니다. 같은 모델의 스텝, LoRA 버전, 프롬프트, 옛 판만 합친다(2026-10-23). 다른 베이스 모델을 '옛 버전'으로 뺐다가 복구한 일이 있다.
- 모델이 업데이트된 뒤의 옛 결과 영상과 대조시트는 품질 판단 근거로 쓰지 않는다. 현재 모델, 샘플링, 노트로 판단한다(2026-10-23).
- 뺀 파일은 지우지 말고 별도 `중복제거됨` 폴더에 원래 경로대로 옮긴다. 무엇이 빠졌는지 풀네임으로 보고한다(2026-10-23). 삭제와 제외는 배포본에만 적용하고 원본, 과거 증거, 이전 ZIP은 보존한다(2026-11-08).
- 새 파일을 기존 묶음에 넣을 때는 내용 기준으로 비교해 겹치는 것은 빼고 겹치지 않는 것만 추가한다. 기존 파일은 바이트 동일을 확인한다(2026-11-08).
- 사용자가 기존 것이 낫다고 한 항목은 대표 정리 대상에서 빼고 그대로 둔다(2026-10-23).

## 9. 잘 나오는 기본값 유지

- 이미 잘 나오는 워크플로는 기본 샘플링, 해상도, 조건을 건드리지 않는다. 결과를 바꾸는 개선은 끄고 켜는 선택 옵션으로 넣고 시험하지 않은 값을 기본으로 바꾸지 않는다(2026-10-14). 실행이 멈추거나 값이 밀리거나 규격이 어긋나는 결함을 고치는 정확도 수정은 기본 경로에서 바로 고친다(2026-10-14). 기본값을 바꿨다가 어둡고 뭉개져서 되돌린 일이 근거다.
- 테스터가 가장 좋다고 평가한 그래프가 있으면 대표로 채택한다. 정확도 수정, 요청받은 스위치, 라이브러리 색·배치만 최소로 고치고 다른 모델 버전도 그것에서 파생한다(2026-10-14).
- 검토 요청을 받으면 스스로 검증하고 논문·공식 자료를 확인한 뒤, 고칠 것만 고치고 문제 없는 파일은 그대로 통과시킨다(2026-10-14, 2026-10-22).
- 개선 작업은 기존 워크플로의 전체 틀 안에서 한다. 구조를 크게 바꾸거나 무겁게 만들지 않는다(2026-10-04, 2026-10-14).
- 결과물 한 건을 스크립트로 대신 만들어 끝내지 않는다. 요청이 워크플로라면 워크플로를 고쳐서 Cloud에서 돌아가게 한다(2026-10-14).

## 10. 모델 선택

- 작업을 시작할 때 모델·LoRA의 최신판과 업데이트를 확인하고, 비교해서 나은 것만 교체한다. 최신이라는 이유만으로 바꾸지 않는다(2026-11-01, 2026-11-09).
- 기존 워크플로와 같은 작업으로 비교해 확실히 나은 상위 버전만 준다. 후보를 많이 뿌리지 않고 나아진 게 없는 폴더는 건드리지 않는다(2026-11-08).
- 새 모델·LoRA를 찾을 때는 최근 업데이트, 다운로드 수, 좋아요 수를 함께 보고 확인한 근거를 제시한다(2026-10-13, 2026-10-22~2026-10-30).
- 개선 전에 깃허브, 허깅페이스, 논문, 공식 자료를 찾는다. 제작자나 커뮤니티의 검증된 워크플로에서 출발해도 된다(2026-09-24).
- 교체 전에 대상 워크플로 풀네임, 기존과 새 파일명, 차이를 먼저 설명하고 결정을 받는다. 지시가 없으면 유지다(2026-10-23).
- 결과를 직접 만드는 메인 모델은 공식이거나 출처가 분명한 파일을 우선한다. 프롬프트 보조 모델은 제작자가 테스트한 조합이면 그대로 둘 수 있다(2026-10-23).
- 모델 전용 설정을 따르고 LoRA를 겹치지 않는다. 일반 편집 LoRA와 FFP LoRA 동시 사용 금지, Pika 6스텝에 Turbo·VFX LoRA 추가 금지, 이미 합쳐진 모델에 같은 LoRA 재적용 금지다(2026-11-08).
- 기본값 모델은 Cloud에 실제로 있는 이름이어야 한다. 시험에 쓴 모델과 배포 JSON의 기본값이 달라서는 안 된다(2026-11-08). 가져온 모델은 Cloud 자산 이름으로 적고 다운로드 URL을 함께 넣는다.
- 새 모델이나 기능은 먼저 Cloud의 `object_info`와 모델 목록으로 지원 여부를 확인한다. 전용 노드가 없으면 정확한 노드명과 출처를 적어 '실행 불가'로 기록한다. 다른 모델이나 근사판으로 바꿔 놓고 그 모델이 성공했다고 표기하지 않는다(2026-11-08).
- Cloud에 올렸을 때 모델 누락 말고 다른 오류가 나는지 확인하고, 있으면 Cloud에서 되는 것으로 대체한다(2026-10-04).
- 현재 Cloud 계정에 없는 모델은 안내문에 가져오기 대상으로 적는다. 사용자가 맡기면 문제 패널이나 가져오기 기능으로 직접 가져와 실행까지 한다(2026-11-08). 저장소를 통째로 가져오지 않고 필요한 파일만 가져온다.
- 모델 링크는 Cloud '모델 가져오기'에 바로 넣을 수 있는 허깅페이스 또는 Civitai 직접 링크로 준다. 게이트 저장소는 토큰 없이 받을 수 있는 공개 대체 링크를 함께 준다(2026-09-27).
- 사용자는 H3와 LTX를 가장 신경 써 달라고 했다(2026-10-13, 2026-11-08). 시간과 크레딧을 나눌 때 이 둘을 먼저 챙긴다.

## 11. 속도와 무게

- 워크플로는 실사용 가능한 속도여야 한다. 무거운 모델은 터보·가속 LoRA를 기본으로 하고, 품질 모드는 스위치로 분리하며, 필요하면 축소 추론 후 원본 크기로 복원한다(2026-10-22~2026-10-23).
- 28스텝은 기본값으로 쓰지 않는다. 무거운 요인을 덜어내되 품질은 유지한다. 스텝을 줄일 때는 같은 영상, 같은 시드로 기존과 비교한다(2026-11-07). 현재 라이브러리의 구성별 스텝은 ref2v Turbo 4(HeadSwap, CharacterSwap, 아웃페인팅, 프리비즈), ref2v Turbo 8 768p(H3 VFX, FFP), H3 Ripple과 Pika 6, fl2v Turbo 8(연장, 모션FX)이다. 스텝 A/B는 576×736, 124프레임에서 잰 것이고 다른 구성으로 넓히지 않는다.
- 요청받은 가속 모델을 Cloud에서 못 쓰면 이유를 밝히고 Cloud에서 되는 대안으로 대체한다. 대안을 원래 모델 이름으로 부르지 않는다(2026-11-07).

## 12. 납품 형식

- 결과는 ComfyUI에 바로 끌어다 놓을 수 있는 JSON으로 준다(2026-09-26, 2026-10-23).
- 끝난 것부터 먼저 준다(2026-11-07). 재납품은 수정한 폴더와 파일만 먼저 준다(2026-10-13).
- 수정본과 최종본을 섞어 주지 않는다. 한 작업은 최종 파일 하나로 끝낸다(2026-10-21).
- 요청이 있으면 수정된 JSON만 ZIP으로 준다. 비교 이미지 등은 넣지 않는다(2026-11-07). 사용자가 그대로 갈아 끼울 수 있게 한다(2026-10-22).
- 사용자가 직접 추가하겠다고 하면 Cloud에서 실제로 돌아간 JSON만 건넨다(2026-11-08).
- ZIP과 최상위 폴더 앞에 `MMDD_` 날짜를 붙인다. 안의 JSON에는 날짜를 넣지 않아 01·02 순서를 유지한다(2026-11-08).
- ZIP은 다운로드 폴더에도 넣고 실제로 열리는 경로를 알린다. 깨진 상대 링크를 주지 않는다(2026-11-08).
- 납품 전에 SHA256 목록, ZIP CRC, 압축 해제 후 파일 일치, 실제 개수, 제외 대상 부재, 참조 파일 포함 여부를 확인하고 이전 ZIP은 보관한다(2026-11-08).
- 검증 작업에는 어디가 완벽하고 어디를 고쳤는지 파일별로 정리한 보고서를 함께 낸다(2026-10-21).
- 수정 보고에는 중요도순 문제 목록, 수정된 JSON, 변경한 노드·설정과 이유, 시작 설정, 같은 시드 비교 절차, 남은 한계와 미확인 항목, 참고 링크를 포함한다(2026-09-27).
- 비교 영상을 요청받으면 VFX 교체 모델별로 원본과 교체 영상을 나란히 붙인 MP4를 만들고 위에 모델 이름을 넣는다. 기존 결과를 잇는 작업이면 다시 생성하지 않는다(2026-11-08). 소개용 비포·애프터 영상은 글씨를 최소화하고 슬라이드 형식으로 노드 화면을 보여 주며, 끊김 없이 부드럽고 구성이 정돈되어야 한다.
- 규칙과 수정본을 공개 저장소에 올려 다른 컴퓨터에서도 같은 방식으로 작업하게 한다. 공개본에는 개인, 계정, 비밀 정보를 넣지 않는다(2026-11-09).

## 13. 보고와 정직성

- 보고와 문서는 한국어로 쓴다. 코드, 노드명, 경로는 그대로 둔다(2026-09-26, 2026-10-22).
- 정적 검증과 실행 검증을 구분하고 실제로 검증한 범위를 밝힌다. 실행하지 못했으면 실행 성공이나 화질 개선을 확인했다고 말하지 않는다(2026-09-27). 렌더를 돌리지 않았으면 돌리지 않았다고 분명히 말한다(2026-10-23).
- 결과는 확정 결함, 원인 후보, 추가 확인 필요로 나눈다(2026-09-27).
- 측정 안 한 품질 향상은 주장하지 않는다(2026-11-08).
- 관측 조건을 넘어 일반화하지 않는다. 패딩 길이를 실제 영상 길이로 성공했다고 쓰거나 특정 해상도 실패를 '항상 실패'로 쓰지 않는다. 추론 해상도와 보간 확대 여부를 적는다(2026-11-08).
- 실행 완료와 시각 통과를 분리한다. 부분 성공은 숨기지 않고 별도로 표시한다(2026-11-08).
- 다른 검수자가 없으면 혼자 판정한 사실과 확인한 프레임 수를 밝힌다(2026-11-08).
- 안내문에는 현재 상태를 맨 앞에 쓴다. 과거의 'GPU 미실행' 문구나 옛 사용법을 남겨 새 안내와 충돌시키지 않는다(2026-11-08). 안내문, 기본값, 노드 제목은 실제 동작과 일치시킨다(2026-09-27).
- 상태표에는 모든 워크플로를 빠짐없이 넣는다. 판정, 불가 사유, 배포 여부, FFP 설정 여부, 메인 서브그래프 정리·검증 여부를 적는다(2026-11-08).
- 시험 범위가 일부뿐이면 '전체 시험 아님'이라고 밝힌다(2026-11-08).

## 14. 작업 원칙과 보안

- 개발 전에 어떤 방식으로 진행할지 스스로 계획을 세운다. 일반적인 구현 선택은 판단해서 처리하고 진행을 막는 정보만 질문한다(2026-09-27, 2026-10-13).
- 범위가 여러 번 바뀌면 가장 마지막 사용자 지시가 이전 지시 전체를 덮는다. 최신 범위를 상태 파일 한 곳에 적고 이전 개수나 목록은 '대체됨'으로 표시한다(2026-11-08).
- 스킬과 하네스를 써서 전문가 수준으로 꼼꼼하게 작업한다. 사용자가 정한 시간과 사용량 상한이 있으면 그 안에서 깊게 조사하고, 상한에 닿기 전에 현재 사용량을 보고한다(2026-11-06).
- 할 수 있는 일을 사용자에게 넘기지 않는다. Cloud 테스트는 켜져 있는 앱과 브라우저에서 직접 끝까지 진행하고, 로그인처럼 대신할 수 없는 일만 정확히 요청한다(2026-10-09).
- 사용자에게 파일을 다시 요구하기 전에 이미 있는 납품본과 Cloud 자산에서 해결한다. 시험 재료는 직접 만들거나 찾아 쓴다(2026-11-08).
- 실행 중인 사용자 작업과 GPU 작업은 취소하지 않는다. 사용자가 특정 작업을 지목했을 때 그 작업만 취소한다(2026-11-08).
- 원본 파일에 덮어쓰지 않는다. 새 기능은 새 파일로 추가하고 수정본은 새 번호나 새 폴더로 만든다. 사용자가 손댄 파일은 요청한 연결만 바꾼 뒤 새 이름으로 저장한다(2026-09-27, 2026-11-05, 2026-11-08).
- 로그인, 토큰 발급·입력, 권한 변경은 사용자가 직접 한다. 약관 동의는 대상을 명시한 허락이 있을 때만 한다. 다른 작업자용 설정 안내도 토큰 값을 채팅에 받지 않도록 쓴다(2026-10-21).
- 이미 쓰고 있는 인증을 그대로 쓰고 자격증명을 추출하지 않는다. CSP 등 보안 설정을 바꾸거나 약화하지 않고 일반 업로드 경로를 쓴다. 새 확장 설치나 권한 확대로 파일을 옮기지 않는다(2026-11-08).
- 계정 메뉴나 이메일이 보이는 스크린샷은 증거로 저장하지 않는다(2026-11-08).
- 미공개 소스는 공개 샘플과 썸네일에 쓰지 않는다. 같은 인물이 나오는 파생 이미지까지 확인해서 뺀다(2026-10-22).
- 시험에는 사용자가 이번 작업의 시험용으로 직접 준 소스를 쓴다(2026-10-21). 그 밖에는 공개·비노골적 자료만 쓰고, 사용자의 다른 작업이나 개인 자료를 찾아서 쓰지 않는다(2026-11-08).

## 15. 범위 결정

- 미해결이거나 한계가 뚜렷한 워크플로는 배포에서 뺀다(2026-11-08).
- 사용자가 유지를 결정하면 한계 있는 파일도 두되, 실패 조건을 안내문과 파일 이름에 경고로 넣는다. 추천 항목으로 표시하지 않는다(2026-11-08).
- 통과한 모델×기능 조합만 활성 폴더에 넣고, 실패·실행 불가 JSON은 보고서와 증거에만 남긴다(2026-11-08).
- Cloud에서 안 되는 파일은 납품하지 않는다(2026-11-08). `90_유료API·스토리보드_미실행`은 사용자가 시험에서 뺀 예외다.
- 유료 API와 스토리보드 계열은 수정·실행 검증 대상에서 뺀다. 원본 그대로 두고 상태표에 '사용자 요청 제외'로 적으며 폴더 이름에 미실행을 표시한다(2026-11-08). 폴더 이름만 보고 유료 API로 분류하지 않고 중첩 서브그래프까지 실제 노드로 판단한다.
- 일반 H3 VFX Edit는 교체용만 유지하고 리무브 프리셋, 예시, 권장은 뺀다. 후반에 새 물체가 생긴 시험이 근거다(2026-11-08).
- 2026-11-08에 MOSS(얼굴·구도가 달라짐), H3 인페인팅(후반에 교체한 의상이 약해짐), LTX BFS(Cloud에 필요한 노드 없음)를 배포에서 뺐다. H3 PersonRemover는 같은 날 유지로 뒤집혔고 근접 인물 실패를 이름과 안내문에 밝힌다. 뺀 항목은 그 실패 조건을 넘었다는 시험 없이 다시 넣지 않는다.

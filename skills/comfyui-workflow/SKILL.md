# ComfyUI 워크플로우 작업 규칙

사용자는 어느 컴퓨터에서 요청하든 같은 방식으로 작업되기를 원한다(2026-11-09 지시). 구조, 자동화, 검증, 납품 방식을 세션마다 새로 정하지 않는다. 이 문서의 절차를 그대로 따른다.

- 답변, 진행 보고, 문서는 모두 한국어로 쓴다. 코드, 노드명, 경로, 파일명만 원문으로 둔다.
- 워크플로 라이브러리는 이 저장소의 `workflows/`에 있다. 시작 안내는 `workflows/00_어떤걸쓸까.md`다. 저장소 안에서 작업하면 스킬 폴더 기준 `../../workflows/`다. `install.sh`나 `install.ps1`로 설치한 스킬이면 스킬 폴더의 `REPO_PATH` 파일에 적힌 저장소 경로를 쓴다. 둘 다 없으면 저장소 위치를 사용자에게 묻는다. `12_NSFW`는 공개 저장소에 없다(`.gitignore`). 없어도 결함이 아니다.
- 도구는 이 스킬 폴더의 `tools/`에 있다. `tools/validate_workflow.py`, `tools/audit_models.py`, `tools/check_public.py`. 쓰기 전에 각 파일 머리말의 사용법을 읽는다. 이 문서의 경로는 모두 이 스킬 폴더 기준이다. Windows에서 `python3`가 없으면 `py -3 -I`로 실행한다.
- 지시가 서로 충돌하면 시간상 가장 마지막 사용자 지시를 따른다. 이 스킬보다 사용자의 현재 지시가 우선한다.
- 이 문서의 사실에는 측정 날짜가 붙어 있다. Cloud와 모델은 계속 바뀌므로, 오래된 사실이 결과를 좌우하면 다시 확인한다.

## 1. 먼저 할 일

### 1-1. 요청 종류를 정하고 해당 참고 문서를 읽는다

| 요청 | 먼저 읽을 문서 | 결과물 |
|---|---|---|
| 새 워크플로 제작 | `references/요구사항.md`, `references/노드_함정.md`, `references/클라우드_사실.md` | 실행되는 JSON 새 파일 |
| 기존 파일 수정·디벨롭 | 위와 같음, 해당 파일의 안내 노트 | 새 이름이나 새 폴더의 수정본 |
| 검수·전수 점검 | `references/테스트_절차.md`, `references/요구사항.md` | 파일별 보고서, 고칠 것만 고친 수정본 |
| 모델·LoRA 최신 확인 | `references/모델_최신확인_절차.md` | 기능별 날짜·좋아요·다운로드 대조표, Cloud 테스트를 통과한 모델로 실제 교체 |
| 에러 해결 | `references/노드_함정.md`, `references/클라우드_사실.md` | 고친 JSON과 원인 |
| 폴더·이름 정리, 중복 제거 | `references/요구사항.md`의 이름·폴더, 중복 절 | 실제로 옮긴 폴더 |
| 모델 링크 요청 | `references/클라우드_사실.md`의 2절 | 직접 다운로드 링크만 |
| 비교·추천 질문('이거 어때?', '둘 중 뭐 써?', '성능 순서') | 해당 JSON의 실제 값, `references/테스트_절차.md` 6절 | 짧은 답. 풀네임, 실제 설정 차이, 측정 여부 |
| 비교 영상, ZIP 납품 | `references/요구사항.md` 12절 | 요청한 파일만 |

사용자가 파일명이나 `blob` 주소만 주고 "링크"라고 하면, Cloud '모델 가져오기'에 바로 붙일 수 있는 `https://huggingface.co/<repo>/resolve/main/<경로>` 직접 링크를 준다. 파일명이 `Owner__Repo__file` 형식이면 HF tree API로 저장소 안 실제 경로를 찾아 200 응답까지 확인한다. Cloud 이름의 `Repo`는 저장소 이름에서 점이 빠진 형태다(`LTX-25`는 `LTX-2.5`). Civitai 주소도 가져오기에 쓸 수 있다. 게이트 저장소이거나 사용자가 다운로드 실패를 알리면 토큰 없이 받을 수 있는 공개 대체 링크도 같이 준다.

### 1-2. 기준 파일을 정한다

- 시작점은 사용자가 지정한 최신 버전이다. 그 이전 원본으로 돌아가 다시 만들지 않는다.
- 사용자가 다시 저장한 파일이 있으면 그 파일을 기준으로 고친다. 사용자가 추가한 노드는 유지한다.
- 저장소를 쓰는 경우 저장소 폴더에서 `git pull`로 최신 라이브러리를 받는다. 스킬 파일이 바뀌었으면 `sh install.sh`(Windows는 `powershell -ExecutionPolicy Bypass -File install.ps1`)를 다시 실행한 뒤 시작한다.
- 파일을 다시 달라고 하기 전에 이미 있는 라이브러리, 납품본, Cloud 자산에서 찾는다.

### 1-3. 원본을 보호할 준비를 한다

원본 JSON은 덮어쓰지 않는다. 기존 파일이 계속 그대로 동작해야 하기 때문이다. 수정본은 새 폴더에 복사해서 만든다. 압축에서 푼 폴더나 받은 워크플로 폴더 안에서는 스크립트를 실행하지 않고, 스크립트는 다른 폴더에 두고 `python3 -I`로 실행한다. 파일명은 NFC로 다룬다. JSON은 `json.dump(obj, fh, ensure_ascii=False, indent=1)`로 저장한다.

### 1-4. 계획을 세우고 진행한다

일반적인 구현 선택은 스스로 판단한다. 질문은 진행을 막는 정보만 한다. 범위가 여러 번 바뀌는 작업은 현재 범위를 작업 폴더의 `작업상태.md` 한 곳에 적고, 옛 개수나 목록에는 '대체됨'을 표시한다. 같은 폴더를 쓰는 다른 세션이 있을 수 있으면 대량 이름 변경 전에 최근 수정 시각을 확인한다. 실행 중인 사용자 작업과 GPU 작업은 사용자가 지목하지 않는 한 취소하지 않는다.

## 2. 작업 절차

### 단계 1. Cloud에서 되는지 먼저 확인한다

모든 파일은 Comfy Cloud에서 추가 설치 없이 돌아가야 한다. 코어 노드와 Cloud 사전 설치 팩만 쓴다. 새 모델이나 기능은 Cloud의 `object_info`와 모델 목록으로 먼저 확인한다. 전용 노드가 없으면 정확한 노드명과 출처를 적어 '실행 불가'로 기록한다. 다른 모델이나 근사판으로 바꿔 놓고 원래 모델이 성공했다고 쓰지 않는다. 자세한 내용은 `references/클라우드_사실.md`에 있다. `90_유료API·스토리보드_미실행` 폴더는 수정과 실행 검증 대상이 아니다. 원본 그대로 두고 상태표에 '사용자 요청 제외'로 적는다(2026-11-08).

### 단계 2. 모델과 LoRA의 최신 상태를 확인한다

워크플로를 만들거나 점검할 때마다 확인한다. 기능별로 파일 날짜, 좋아요, 다운로드 수를 Hugging Face와 Civitai에서 함께 대조한다. 날짜와 호환성만 보고 "유지"로 끝내지 않는다(2026-11-09 지시). 더 새롭거나 인기가 많고 Cloud에서 돌아가는 파일은 교체 후보로 올리고, 같은 입력과 시드로 Cloud에서 비교해 원본 보존·색감·모션이 나빠지지 않으면 실제로 교체한다. 떨어진 후보는 파일명과 이유를 표로 남긴다. Cloud에 없는 노드 팩이 필요한 후보는 인기와 상관없이 실행 불가로 표시한다. 같은 점검에서 겹치는 워크플로, 무거운 원인, 파일별 터보 적용 가능 여부도 함께 본다. 워크플로가 무거워지면 안 된다. WAN은 우선순위가 가장 낮아 H3·LTX를 끝낸 뒤 시간이 남으면 마지막에 한다. 절차와 현재 판정은 `references/모델_최신확인_절차.md`에 있다. 파일 하나를 고치는 요청이면 그 파일의 모델만 `python3 -I tools/audit_models.py <파일>`로 본다.

### 단계 3. 그래프를 라이브러리 양식으로 만든다

같은 폴더의 기존 파일에서 노드 형태를 복제해서 시작한다. 공식 템플릿이나 외부 워크플로를 그대로 붙여 넣지 않는다.

- 구조는 `입력 로드 → 메인 서브그래프 노드 1개 → 저장`이다.
- 프롬프트, 길이, 해상도, 시드 1개, 스위치, 모델 선택처럼 사람이 바꾸는 값만 메인 노드 위젯으로 올린다. 라벨은 한국어로 쓴다.
- 서브그래프 안은 번호 붙은 한글 그룹으로 나눈다. 모델끼리, 샘플러끼리 모은다.
- 노드는 최소로 쓴다. 문어발처럼 늘어진 그래프를 만들지 않는다.
- 한 번 실행에 최종 저장은 1개다. 패스 추출처럼 결과가 원래 여럿인 파일과 사용자가 고른 멀티모델 비교 원본만 예외다.
- 안내는 짧은 사용법 노트와 모델·설정·한계 상세 노트로 나눈다. 모델 다운로드 주소는 `properties.models`에 넣는다.

### 단계 4. 크기·길이·FPS를 자동화한다

작업자가 크기나 길이를 계산하게 하지 않는다. 입력에서 가로·세로·프레임 수·FPS를 읽어 모델 규격에 맞추고, 생성 후 원본 값으로 되돌린다. 모델 프레임 규칙 때문에 끝을 잘라내지 말고 패딩해서 생성한 뒤 원래 길이로 자른다. 생성 해상도는 메가픽셀 값 하나로 조절하고 가로세로는 원본 종횡비로 계산한다. 규격이 어긋나면 잘못된 결과를 저장하지 말고 멈춘다. 단 29.97처럼 표기만 다른 FPS에서 멈추면 안 된다. 이 규칙은 원본 영상을 편집하는 파일에 적용하고, 아웃페인팅, 영상 연장, 프레임보간·슬로모션, 업스케일처럼 기능 자체가 규격을 바꾸는 파일은 그 항목만 예외다(`references/요구사항.md` 3절). 납품용 영상의 기본 출력은 무음이고, 소리를 쓰는 파일도 모델 생성 효과음은 기본으로 끈다. 오디오 트랙이 없는 소스에서 멈추면 안 된다(`references/요구사항.md` 3절).

### 단계 5. 바꿀 곳만 바뀌게 만든다

합격 기준은 '바꾼 곳만 바뀌었는가'다. 수정 대상 밖의 색, 명암, 움직임, 프레임은 원본과 같아야 한다. 결과의 k번 프레임은 원본 k번 프레임과 대응해야 한다. 색이 틀어지면 보정 노드를 덧대기 전에 모델 제작자의 프롬프트 가이드에 맞춰 원인부터 잡는다. 마스크는 흰색이 바꿀 곳이고, 마스크를 받는 파일에는 기본 꺼짐의 '마스크 반전' 스위치를 둔다.

### 단계 6. 프롬프트를 모델 규칙대로 쓴다

모델별 트리거, 이미지·비디오 토큰, 참조 역할을 따른다. 기본 프롬프트는 완성된 문장이어야 한다. 모든 모델에 같은 문장을 쓰지 않는다. 접두사와 문장 규칙은 `references/요구사항.md`의 프롬프트 절에 있다. 실제 인코더에 들어간 문장까지 확인한다.

### 단계 7. 배치와 이름을 맞춘다

메인 화면은 입력 왼쪽, 프롬프트·핵심 설정 가운데, 결과 오른쪽, 안내문 아래다. 노드 겹침은 0이다. 파일 이름은 `폴더내순서_모델+버전_기능_입력조건_실측초[_모델별순위].json`이다. 끝의 초는 Cloud 실측값이고, 재지 않았으면 넣지 않는다.

### 단계 8. 정적 검증을 돌린다

`python3 -I tools/validate_workflow.py <파일이나 폴더>`를 실행하고 error를 0으로 만든다. 이 검사는 구조만 본다. 통과가 실행 성공을 뜻하지 않는다. `widgets_values_named`의 값 일치와 서브그래프 위젯 순서는 `references/노드_함정.md` 1절을 보고 따로 확인한다. 중첩 서브그래프 정의 순서는 이 도구가 잡는다.

### 단계 9. 실제 프런트엔드로 왕복 검증한다

정적 검사는 프런트엔드 전용 값 밀림을 놓친다. `loadGraphData` 뒤 `graphToPrompt` 결과를 의도한 그래프와 비교하고, 메인 위젯을 기본값과 다른 숫자로 바꿔 내부 API까지 전달되는지 본 뒤 되돌린다. 절차는 `references/테스트_절차.md` 3절에 있다.

### 단계 10. Comfy Cloud에서 실제 생성까지 돌리고 측정한다

불러오기 확인으로 끝내지 않는다. 추가하거나 수정한 파일은 실제 생성까지 돌린다. 원본·레퍼런스와 대조해 움직임, 색, 레퍼런스 반영, W×H, 프레임 수, FPS를 숫자로 기록한다. 납품 전 전체 점검은 파일을 하나씩 살피되, GPU 실행은 필요한 파일을 골라 한다(2026-11-09 지시). 고르는 기준은 `graphToPrompt` 결과가 바뀐 파일, 기존 성공 증거와 설정이 다른 파일, 정적·왕복 점검에서 의심이 나온 파일이다. 배치만 바꾼 파일은 전후 동일성으로 끝낸다. 대표 1개 성공을 전체 성공으로 부르지 않는다. 고친 파일은 다시 돌린다. 사용자의 Cloud 로그인이 끊겼으면 로그인만 요청하고, 나머지는 직접 끝까지 진행한다.

### 단계 11. 납품한다

- 설명 자료가 아니라 바로 실행되는 JSON을 준다. 폴더 정리 요청이면 실제로 옮긴다.
- 끝난 것부터 먼저 준다. 전부 끝날 때까지 쥐고 있지 않는다(2026-11-07 지시).
- 수정분만 요청받으면 수정된 JSON만 ZIP이나 별도 폴더로 준다.
- ZIP과 최상위 폴더 앞에 `MMDD_`를 붙인다. 안의 JSON에는 날짜를 넣지 않는다.
- ZIP 납품 전에 SHA256 목록, CRC, 압축 해제 후 일치, 실제 개수, 제외 대상 부재, 참조 파일 포함 여부를 확인한다. 이전 ZIP은 보관한다.
- 파일은 실제 경로와 풀네임으로 알린다. 사용자에게 보이는 위치에 있는지 확인한다.
- 공개 저장소에 올리면 먼저 `python3 -I tools/check_public.py <폴더> [--deny-file 개인단어목록.txt]`로 개인·계정·비밀 정보가 없는지 확인한다. 개인단어목록 파일은 저장소에 넣지 않는다.
- 라이브러리에 파일을 넣거나 이름을 바꾸면 `00_어떤걸쓸까.md`의 순서·측정값과 옛 경로·새 경로 대응표도 같이 고친다.

## 3. 하면 안 되는 일

이 항목들은 실제로 사용자의 시간과 크레딧을 낭비했거나 결과를 망친 일, 또는 사용자가 금지한 일이다.

1. 원본 파일을 덮어쓰기. 사용자가 손댄 파일에서 요청하지 않은 연결이나 노드를 바꾸기.
2. 잘 나온다고 확인된 그래프의 기본 샘플링·해상도·조건을 시험 없이 바꾸기. 개선은 끄고 켜는 선택 옵션으로 넣는다.
3. 렌더를 돌리지 않고 실행 성공이나 화질 개선을 말하기. 정적 통과를 '완료'라고 부르기.
4. 측정하지 않은 품질 향상을 주장하기. 시험 조건을 넘어 일반화하기.
5. 다른 모델로 바꿔 놓고 원래 모델 이름으로 성공 표시하기.
6. 요청이 워크플로인데 결과물 한 건만 스크립트로 만들어 끝내기.
7. 공식 템플릿에 노트만 붙여 납품하기. 템플릿의 예제 이미지, 예제 프롬프트, 랜덤 시드를 기본값으로 남기기.
8. 원본 끝을 잘라 프레임 규칙을 맞추기. 임의 크롭, 프레임 드랍.
9. 마스크 없는 경로를 '픽셀 보존'이라고 부르기. 생성 전체 프레임을 '원본 보존 참조'라고 부르기.
10. LoRA 겹쳐 쓰기. 일반 편집 LoRA와 FFP LoRA 동시 사용, Pika 6스텝에 Turbo·VFX LoRA 추가, 이미 합쳐진 모델에 같은 LoRA 재적용.
11. JSON 안내문이나 파일 이름을 실제 동작의 증거로 믿기. 안내문은 검증 대상이다.
12. 가져올 수 없거나 Cloud 이름 규칙에 맞지 않는 이름을 기본 모델로 두고 안내문으로 '직접 바꾸세요'라고 때우기. 시험에 쓴 모델과 배포 기본값이 다른 상태로 납품하기. `Owner__Repo__file` 이름에 `properties.models` 주소가 있고 현재 계정에 가져오기만 하면 되는 모델은 안내문에 가져오기 대상으로 적는다.
13. 유료 파트너 노드를 사용자 승인 없이 돌리기.
14. 로그인, 토큰 입력, 권한 변경을 대신하기. 키나 토큰 파일을 읽거나 인증값을 추출하기. CSP 같은 보안 설정을 바꾸거나 우회하기. 채팅으로 토큰 값을 받기.
15. 계정 메뉴나 이메일이 보이는 화면을 증거로 저장하기. 이번 시험용으로 받지 않은 사용자의 다른 작업이나 개인 자료를 시험에 쓰기. 공개본에 이름, 계정, 비밀값, 로컬 경로를 넣기.
16. 의미 없는 재시도 반복. 원인에 맞는 변수를 하나 바꾸고, 안 되면 사실대로 보고한다.

## 4. 보고 형식

모든 보고는 한국어로 쓰고 아래 순서를 따른다. 해당 없는 항목은 뺀다.

```
## 결과
한두 문장. 무엇이 되었고 무엇이 안 되었는지.

## 파일
실제 경로와 풀네임. 수정 파일과 그대로 둔 파일을 구분.

## 문제와 수정 (중요도순)
| 파일 | 구분(확정 결함 / 원인 후보 / 추가 확인 필요) | 내용 | 변경한 노드·설정 | 이유 |
시작 설정, 같은 시드로 비교하는 절차, 참고한 공식 자료 링크를 적는다.

## 검증 범위
| 파일 | 정적 | 프런트 왕복 | Cloud 실행 | 시각 판정 | 측정값 |
입력 조건(W×H, 프레임, FPS, 추론 해상도), 시드, job ID를 적는다.
실행하지 않은 것은 '미실행'이라고 적는다.

## 한계와 미확인
클립 몇 개로 시험했는지, 다른 검수자 없이 혼자 판정했는지, 확인한 프레임 수.

## 사용자 결정이 필요한 것
모델 교체 후보는 대상 파일 풀네임, 기존·새 파일명, 차이, 근거 링크.
```

긴 검증 작업에는 어디가 완벽하고 어디를 고쳤는지 파일별 보고서를 같이 낸다. 사용량 상한을 지정받았으면 그 안에서 작업하고, 상한에 닿기 전에 현재 사용량을 보고한다.
